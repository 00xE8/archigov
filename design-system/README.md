Carbon is an open-source design system for products and digital experiences: a productive, grid-based, square-cornered language built on IBM Plex and a 2px/8px spacing rhythm. Use these rules when building with it.

## Content fundamentals

- **Sentence case everywhere**: buttons, labels, headings, tabs, menu items (“Create project”, not “Create Project”). Proper nouns keep their capitals.
- **Lead with the verb** on actions: “Add item”, “Download report”, “Delete orders-prod?”. A confirmation repeats the object it acts on.
- **Address the user as “you”**; the product speaks plainly, never as “we” unless it is the organisation.
- **Be brief and specific.** Labels are nouns (“Region”, “Email”); helper text says what is expected (“Lowercase letters, numbers and dashes.”); error text says how to fix (“Enter a valid email address.”).
- **No emoji, no exclamation marks** in UI copy. Status is carried by an icon plus a word.
- Placeholder text only shows an example (“e.g. Billing API”); never put instructions or required information there — it fails contrast by design (see `text-placeholder`).

## Themes and colour

Four themes, chosen per product or zone with `data-theme`: **White** (`white`, the default), **Gray 10** (`g10`), **Gray 90** (`g90`) and **Gray 100** (`g100`). Always build with the semantic tokens below; the palette steps (`blue-60`, `gray-80` …) are the raw values the themes are made from and are for data viz and tags only.

- **Surfaces stack by layer**: page `background` → containers `layer-01` → nested `layer-02` → `layer-03`. Hover and selected states use the matching `layer-hover-0x`, `layer-selected-0x`. Use the `Layer` component to step down a level instead of picking tokens by hand.
- **Fields** sit on `field-01` (on `background`) or `field-02` (on `layer-01`), with a 1px `border-strong-01` bottom rule, never a full outline.
- **Text**: `text-primary` for content, `text-secondary` for labels and secondary copy, `text-helper` for helper text, `text-placeholder` for placeholders, `text-disabled` for disabled, `text-on-color` on any filled colour (buttons, high-contrast notifications), `text-inverse` on `background-inverse`.
- **Interactive**: `interactive` (blue-60 in light themes) for primary actions and selection; `link-primary` for links; `border-interactive` for selected tabs and active rules.
- **Focus**: every focusable element shows a 2px `focus` outline; on filled controls add a 1px inset `focus-inset`. `focus` holds 4.5:1 or more on `background` in every theme.
- **Status**: `support-error`, `support-warning`, `support-success`, `support-info` (and `support-caution-major`/`-minor`). Each status always pairs colour with its icon and a word; success green and error red are never the only difference.
- **One primary blue per view.** Blue is the brand’s only action colour; other hues appear in tags, data viz and status.
- AI-generated content is marked with the `ai-*` tokens (aura gradient, `ai-border-*`, `ai-popover-*`) and the AI label — use them only for AI-produced UI.

## Typography

IBM Plex Sans for everything (`--font-sans`), IBM Plex Mono for code (`--font-mono`), IBM Plex Serif for pull quotes (`--font-serif`). Weights: 300 light, 400 regular, 600 semibold — no bold.

- **Productive** (product UI): set body in `body-compact-01` (14/18) for short text in dense UI and `body-01` (14/20) for paragraphs; labels `label-01`; helper `helper-text-01`; component headings `heading-compact-01`/`heading-compact-02`; page headings `heading-03` → `heading-05`.
- **Expressive** (marketing, editorial): the `fluid-*` styles grow across breakpoints — `fluid-heading-03`…`06`, `fluid-paragraph-01`, `fluid-quotation-01/02`, `fluid-display-01`…`04`.
- Code uses `code-01` inline and `code-02` in blocks.
- Never set type outside the scale; small text keeps its 0.16px or 0.32px letter-spacing.

## Spacing, size and layout

- **Spacing scale** `spacing-01` (2px) … `spacing-13` (160px). Component internals use `spacing-01`–`spacing-05`; layout gaps `spacing-06`–`spacing-13`. Standard padding is `spacing-05` (16px).
- **Component heights** come from the size scale: `size-sm` 32px, `size-md` 40px (default for fields), `size-lg` 48px (default for buttons), `size-xl` 64px. Keep controls in a row at the same size.
- **Icons** are 16px (`icon-size-01`) inside controls and 20px (`icon-size-02`) standalone.
- **Grid**: the 2x grid — 16 columns at large breakpoints (4 at small, 8 at medium), 32px gutters (`spacing-07`). Breakpoints: sm 320, md 672, lg 1056, xlg 1312, max 1584.

## Shape, borders and elevation

- **Square by default.** Buttons, fields, tiles, modals and tables have 0 radius (`border-radius-00`). Pills (`border-radius-max`) are for tags only; the 2–8px radii are reserved for the few components that opt into rounding.
- Separate with **1px rules** (`border-subtle-0x` matching the layer) and with layer steps, not shadows.
- **Shadows** appear only on floating surfaces — menus, popovers, tooltips, toasts — via the `shadow` colour.
- **Motion** is short and functional; no decorative animation. See Motion below.

## Motion

Motion uses the `@carbon/motion` values, loaded as CSS custom properties with `bundle.css` (see the Motion card).

- **Productive by default**: everyday UI uses `--easing-*-productive` with `--duration-fast-01` (70ms) to `--duration-moderate-02` (240ms). Expressive curves and `--duration-slow-01`/`-02` (400/700ms) are for significant moments — opening a panel, a primary action, a system alert.
- **Curve by direction**: `standard` for movement within the view, `entrance` for elements arriving, `exit` for elements leaving.
- **Duration by size and distance**: buttons and toggles `fast-01`; fades of small elements `fast-02`; small expansions `moderate-01`; toasts and larger expansions `moderate-02`; large panels `slow-01`; background dimming `slow-02`.
- **Surfaces** name common transitions: `disclosure` (accordion), `contextual` (tooltip, popover), `expand` (tile → side panel), `invoke` (button → modal or menu). They are experimental upstream.
- Never animate for decoration, never loop, and turn motion off under `prefers-reduced-motion: reduce`.

## Components

The live components are the real `@carbon/react` 1.118.0 and `@carbon/charts-react` 1.27.21 code, bundled together as `window.Carbon` (React 18). Each card’s README gives when to use it, what you supply and its props. Compose screens from these rather than restyling raw elements; wrap a region in `<Carbon.Theme theme="g100">` to switch its theme, or set `data-theme` on the root.

## Data visualisation

Charts are Carbon Charts (`@carbon/charts-react`), exposed on `window.Carbon` beside the components: `SimpleBarChart`, `GroupedBarChart`, `StackedBarChart`, `LineChart`, `AreaChart`, `StackedAreaChart`, `ScatterChart`, `BubbleChart`, `ComboChart`, `DonutChart`, `PieChart`, `GaugeChart`, `MeterChart`, `BulletChart`, `HistogramChart`, `BoxplotChart`, `LollipopChart`, `HeatmapChart`, `RadarChart`, `AlluvialChart`, `TreeChart`, `TreemapChart`, `CirclePackChart`, `ChoroplethChart`, `WordCloudChart`. Each takes `data` (flat records) and `options`.

- **Match the theme**: pass `options.theme` equal to the page’s `data-theme`; the chart picks the light or dark series palette from it.
- **Colours are tokens**: every series, sequential and diverging colour reads this system’s tokens — the 14-series palette from `viz-categorical-*`, everything else from the palette steps (`purple-70`, `teal-50` …). Edit a token and charts follow; hover shades stay Carbon’s.
- **Categorical colour** follows Carbon’s palettes, in order: `viz-categorical-01` … `viz-categorical-14` hold the 14-series palette (light values for White and Gray 10, dark for Gray 90 and Gray 100). For fewer series Carbon Charts uses its own curated 1–5-colour palettes rather than the first n of these; let the chart choose.
- **Sequential** scales (`color.gradient` `mono-1`…`mono-4`) run between white and steps 10–100 of `purple`, `blue`, `cyan` or `teal`; **diverging** scales (`diverge-1`, `diverge-2`) run red ↔ cyan or purple ↔ teal through white. Dark themes reverse the step order so the strongest value stays the most prominent. Use sequential for magnitude, diverging only when there is a meaningful midpoint.
- **Status colours** in gauges, meters and thresholds use the `support-*` tokens and always carry a label.
- **Pick the simplest chart**: bars for comparison, lines for trends, stacked bars or areas for part-to-whole over categories or time; donuts and pies only for ≤6 slices summing to a whole. Start value axes at zero for bars.
- Title every chart in sentence case, label axes with units, and keep the legend and toolbar (table view keeps the data accessible).

### Chart anatomy, axes and legends

Synced from carbondesignsystem.com `building-blocks/core/data-visualization` (chart-anatomy, axes-and-labels, legends), Oct 2026.

- **Anatomy**: a chart is a descriptive, qualitative title (the insight, not the metric), the graph frame, axes with ticks and axis titles, an optional legend, a toolbar/zoom bar when the data warrants navigation, and tooltips. Tooltips appear on hover and repeat the data point's values on both axes plus whatever it needs to stand alone. Prefer labels placed directly on the chart — a legend relies on visual association and is the fallback when direct labels don't fit, not the default. Don't crowd the frame; circular slices under 3° need a callout, and slices under 1° aren't rendered at all.
- **Axes**: bar and area charts start value axes at zero (they encode size); line and scatter charts may crop the Y axis to show trend. Never interpolate across missing data — label the start and end of the gap. An axis break is allowed to bring extremes into view: mark it with a sinusoidal cut in the axis line (X: fluid width, ≥16px; Y: fixed 16px); data falling inside a break drops to 0.5px strokes with no point markers, or the span stays empty. Time axes keep even tick increments — compress with a break, never irregular ticks — and a tick label that crosses into a new day, month or year goes semibold as a landmark.
- **Legends**: bottom by default; top when vertical space is tight (dashboards); left for type alignment; right when space is plentiful. Omit the legend when there is one category or direct labels fit. Interactive legends: hovering an entry drops every other category to 30% opacity; clicking isolates the entry (it shows a checkmark); when every entry is selected the legend resets to default. At most two rows before a "view more"; a legend never exceeds 30% of the chart's height (scroll beyond that). Texture may supplement colour for accessibility.
- **Diagrams (the generated ArchiMate views) follow the same anatomy**: a heading and one-line caption, a toolbar of icon buttons with tooltips (zoom in, zoom out, fit), native tooltips on hover, a bottom legend mapping the layer fills (application blue, technology green, grouping/location gray) with the hover-dim and click-isolate behaviour above, and annotations as the human layer pinned over derived content — authored and audited, never altering the derived geometry. Verification is stated in words beside the diagram, never through styling alone.

## Patterns

Synced from carbondesignsystem.com `building-blocks/core/patterns` (overview and all sixteen pattern pages), Oct 2026. Patterns are best-practice combinations of components — reuse them rather than inventing flows.

- **Common actions** — Add: emphasis by importance, one primary button per view. Cancel: secondary button or link; warn when it loses work. Clear: the × icon at the field's right edge. Close: the icon, top right, never inside a button. Copy: copy icon + a "copied" tooltip after the click. Delete: danger button, danger menu option or danger modal — low impact (easy to undo or recreate) deletes on click, moderate impact confirms with consequences spelled out, high impact makes the user type the resource name; afterwards return to the list, animate the removal and confirm with a success notification. Edit: menu option, button or icon. Remove (reversible, not destroy): subtract icon, never overemphasised, say if it's permanent. Reset: a link, reverts to the last Apply. Errors: say what happened and the way forward — at most three lines full-page, two on a field.
- **Dialogs** — modal only for critical or required work, triggered by the user (background events get a toast); passive · transactional · acknowledgment · progress variants; four fixed sizes, only the body scrolls. Cancel leftmost, primary rightmost, one primary per dialog; buttons full-bleed at the bottom (one: right 50%; two: 50/50; three: 25% each right-aligned). Destructive confirms use the transactional danger modal; the title and primary button name the action — never "OK" or "Done". Focus moves to the first input on open, stays trapped, returns to the trigger on close; Esc closes. Validate before closing: errors keep the dialog open with inline messages; short loads show a spinner over the body with the primary disabled. No nested modals.
- **Disabled, read-only, hidden** — disable what is temporarily unavailable (text 25% / component 50% opacity, not-allowed cursor, invisible to screen readers — so never for content someone must read); read-only keeps content visible, focusable and screen-readable with the interaction removed (transparent field backgrounds, de-emphasised borders, unchanged text colour at 4.5:1, signifier icons in icon-disabled); hide entirely what permissions deny. When a disabled control blocks the primary action, an inline notification explains how to enable it. A disabled control stays disabled inside a read-only view.
- **Disclosures** — click-triggered popovers (toggletips) for optional detail or small controls: at most six columns wide, one open at a time, never auto-opened, never for critical or required input (that is a modal). Dismiss by the trigger, outside click, the × (top right, in empty space), Esc, or tabbing out. A tooltip stays text-only; the moment content is interactive it is a disclosure.
- **Empty states** — replace the component entirely (no orphaned table headers); a short positive title (required), a body that states the next step and why (required), one primary action (button, inline link or pointer), an optional secondary such as a docs link, an optional decorative image (empty alt). Left-align the block; use a tertiary CTA when several empty states share a screen; prefer text-only when many widgets fail at once. Error states say why and what to do — never a dead end, never flippant.
- **Filtering** — single-select behaves like radios (dropdown or radio set), multiselect like checkboxes; filter categories sit left of or above the data, never buried together in one menu; batch application ("Apply filters") for multi-category or slow data, instant for a single category; a closed filter container shows the applied count and can clear from the indicator; every category — and the whole set — clears back to its default in one act.
- **Forms** — top-aligned labels (sentence case, one to three words, no colons), single column unless fields are logically one line, field widths match expected content, 40px inputs; 32px between fields (24/16 in panels and modals), 48px before the buttons; mark the minority "(required)" or "(optional)" and keep the choice consistent; validate on blur with specific error text on the form itself, clear it once fixed, add an inline notification for server errors; the primary button is task-specific and sits at the bottom (left-aligned in page forms, primary-right in dialogs and wizards); disable the primary only on short forms and after submission; pre-fill safe defaults; a dialog holds about five inputs, a side panel more; focus the first required field on load.
- **Global header** — persistent: menu icon · header name (links only to home) · product links left, system links right; utility icons open panels rather than navigate; dropdowns open on click and the chevron flips; product links collapse into the side menu at narrow widths; no unbounded user-created content in the side nav.
- **Loading** — skeletons for containers and data on first load (a few seconds at most; never for buttons, inputs, toasts, menus or a modal itself); a spinner answers a user action (inline on the component; full-screen with overlay only when the whole app is blocked); beyond a moment or two show progress, beyond minutes add a notification; load progressively — skeletons and static text first, data, images and below-the-fold after; screen readers are told when the app is loading, busy, stuck or failed.
- **Login** — ID first, then Continue routes to SSO or the password step behind the scenes (don't make people choose when the system can); one generic message for a wrong ID or password so valid accounts leak nothing; inline validation on blur; after a voluntary logout confirm and land on the login page, after an inactivity logout return the user to where they were. (Carbon words the action "Log in"; this product says "Sign in" — keep one, consistently.)
- **Notifications** — inline (contextual, persists until resolved, at most one ghost action, never covers content) · toast (system-level, top right, ≤3 lines, newest on top, auto-dismiss only when action-free) · callout (loads with the page near the relevant content, persistent, no success/error status, at most one per page) · banner (product-wide, below the header, one at a time) · modal (critical only). High-contrast for urgent, low for supplemental, never mixed within a variant; critical messages never auto-dismiss; always say what to do next.
- **Overflow content** — truncate with an ellipsis (keep ≥3 characters) only on static text and links — never on page headers, titles, labels, errors or notifications; end-line to shorten, front-line when the end identifies, mid-line when both ends matter (JS); truncated text carries the full value in a title tooltip; prefer "Show more"/"Show less" over scrolling, gradients or fades, and "Load more" when performance matters.
- **Status indicators** — red danger/error · orange serious warning · yellow warning · green success · blue passive or in-progress · gray draft/not started · purple outlier. Icon indicators where attention matters most; shape indicators (label mandatory) in tight spaces and for lifecycle; dot and numbered badges for "new" (numbers only on the shell's large icon button); differentials always with an explicit sign or arrow. At least two of colour, shape and symbol — aim for three; 3:1 contrast; legible in grayscale; consolidate multiples to the highest severity; at most five or six indicators per view; never the same shape in different colours.
- **Text toolbar** — a horizontal group of formatting controls above the text area it acts on (actions · formatting · paragraph · insert); toolbar role with arrow-key navigation and a tooltip on every control; extra controls fold into an overflow menu when width runs out.
- **Fluid styles** — fluid components bleed to their container's edges (label inside the 64px field; buttons 25/50/100% wide hugging an edge) for expressive moments inside compound containers; stay default (productive) in anything dense or complex; the common hybrid is default inputs with a fluid button in a modal or side panel; stacked fluid parts need a 3:1 border between them.

## Iconography

Carbon icons: a single-colour, 2px-stroke-style set drawn on a 32px grid and shipped at 16, 20, 24 and 32px. In React use the icon components (`Carbon.Icons.Add`, `.TrashCan`, `.Settings` …) which inherit `currentColor`; size 16 inside buttons and fields. The `Icons` asset group holds a representative subset of the 32px SVG sources. Icons never replace a label on primary actions; icon-only buttons (`IconButton`) always carry a tooltip label. No emoji.

**Motion icons** (`Carbon.MotionIcons`, 151 icons from `@carbon/icons-motion`) are animated versions of the same icons. Animate only in response to the user — on hover or focus of the control that holds the icon, or once when an action completes — and keep the static icon elsewhere. One animation at a time; nothing loops. They draw in `icon-primary` like the static set and stop entirely under `prefers-reduced-motion`.
